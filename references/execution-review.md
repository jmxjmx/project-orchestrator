# 执行、恢复与评审

## 基线与授权

首次实施前：

1. 阅读适用的项目指令和真实代码，检查已有约定与可复用接口。
2. 记录现有测试、构建、已知失败和工作区状态。不要覆盖或 revert 他人的修改。
3. 说明目标、允许修改的路径、依赖或系统变化、预期副作用及回滚方式。
4. 首次修改提案只输出上述范围、验证和回滚信息，然后结束该次回复并等待确认；不得在提出提案的同一轮继续写入。一次确认只覆盖明确范围，不能推导出对外发布、部署或新增权限。

测试、构建或运行也可能写入缓存、数据库、网络或本地状态；根据实际副作用纳入授权，不把它们一概当作只读。

## 小步实施

每个执行单元：

1. 核对前置依赖、任务范围和验收方式。
2. 对行为变化优先写出会失败的测试并确认失败原因正确；不适用时说明替代证据。
3. 只做当前必要实现，不顺手重构或修复范围外问题。
4. 运行聚焦检查，再运行必要的集成或回归检查。
5. 检查实际 diff、生成物和外部状态，记录证据后更新任务状态。

涉及认证、授权、支付、数据删除等保护性控制时，优先提供不削弱保护的测试方式，例如可控时钟、短期测试令牌或测试替身。不要仅为方便测试而关闭或绕过校验；用户仍要求改变保护行为时，先说明影响范围并获得明确确认。

不要为了让测试通过而降低已确认验收标准、删除有效断言或隐藏失败。 flaky 或既有失败要与新失败分开处理。

## 变更与偏差

新证据出现时：

- 根因或假设被推翻：停止沿用旧方案，重新诊断。
- 技术路线变化但意图不变：更新方案和受影响任务，重新验证。
- 需求或范围变化：先提出变更提案，列出新增依赖的数据流、凭据/网络/部署/验证副作用，以及需要更新的 `prd.md`、`plan.md`、`tasks.md` 和具体受影响任务；请求用户决策并重新授权。未获确认前只能提案，不修改文件。
- 发现范围外问题：记录并报告，未经批准不修复。

修正拥有问题的上游产物，不在多个文件中复制相互矛盾的补丁。

## 恢复与幂等

恢复时先核对文件、版本控制、运行环境和外部副作用，再决定下一动作。旧任务状态、摘要或计划只提供线索。

可能重复执行的操作先确认：

- 先前是否已成功，失败是否发生在结果返回之前。
- 操作是否幂等，是否需要唯一标识、事务或补偿动作。
- 回滚是否安全，是否会覆盖他人后续修改。

无法确认外部写入是否成功时，不直接重试不可逆操作。

## 并行与隔离

只有任务相互独立、用户允许且写入范围不重叠时才并行。需要隔离时使用独立工作区或 worktree，并明确基线、依赖安装、生成文件和最终集成责任。

并行不适用于共享数据库、同一文件、全局配置、共同构建锁或未经确认的外部操作。集成后必须重新运行跨切片检查。

## 评审顺序

### 规格评审

- 目标和范围是否与用户请求一致。
- 每个必要需求是否可观察并有验收场景。
- 是否存在矛盾、遗漏、隐藏假设或超出范围的任务。
- 规格、方案、任务和验证策略是否互相一致。

### 实现评审

- 先列出影响正确性、需求符合度、安全或回归的发现，并给出文件位置与证据。
- 再检查可维护性、无关修改和过度设计。
- 区分本次新问题与既有问题，区分必须修复与可选建议。
- 修复具体发现后重新验证，不无限追逐低价值风格意见。

fresh-context 只读评审可用且已获授权时，向评审者提供意图、实际 diff 和必要上下文，不要求其重复实现。没有独立评审条件时明确写 `self-review`。

## 最终验证

按适用情况验证：

- 聚焦测试和相关回归测试。
- lint、typecheck 和构建。
- 应用启动或核心命令实际运行。
- 关键用户流程、错误路径和边界情况。
- UI 的实际浏览器或桌面表现，而非仅凭单元测试。
- 文档中的运行和测试步骤。
- 实际 diff 中没有临时调试、未披露 TODO 或无关变更。

最终回复包含完成状态、修改文件、验证命令和结果、运行/测试方式、剩余风险及下一步。无法执行的检查必须明确列出，不能用“应能通过”代替。

## Windows 中文编码

涉及中文命令行输出时，优先使用 UTF-8 读写。Python 可设置 `$env:PYTHONUTF8='1'`，Node.js 注意控制台代码页。出现乱码时先区分编码问题与业务失败，不要为了消除乱码修改无关逻辑。
