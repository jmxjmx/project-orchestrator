# 工作流路由

先选择任务类型，再选择流程深度。路径定义必要动作，深度决定需要多少产物和评审。不要为了套流程而把简单问题复杂化。

## explore：探索与决策

适用于想法评估、技术选型、可行性研究或问题定义。

1. 先用一句话复述用户原始目标，再明确要支持的决策、目标用户和约束；不要只列方案而遗漏用户想解决的问题。
2. 收集与决策相关的一手证据，区分来源事实、推断和假设。
3. 比较合理选项及更简单的替代方案，说明成本和风险。
4. 输出 `go`、`clarify` 或 `stop`：
   - `go`：证据足以进入规格或实施规划。
   - `clarify`：列出会改变决策的具体未知项。
   - `stop`：记录不投入的理由；停止也是有效成果。

只读探索不修改项目。原型、spike 或落盘报告需要单独符合副作用授权。

## fix：缺陷修复

适用于已有行为不符合已确认意图的情况。新需求不能伪装成缺陷。

1. 记录原始症状、预期行为、环境和复现步骤。
2. 在不改源码的情况下复现；不能复现时说明证据缺口并缩小变量。
3. 定位可证据支持的根因，限定修复范围并获得修改授权。
4. 优先增加能复现缺陷的回归测试，确认修复前失败。
5. 最小修复后重新执行原始复现和相关回归检查。

只有完整复现链和必要检查通过才可标记 `verified`。阶段汇报必须明确说明：其他测试通过不能替代原始症状复现；原始复现未执行或未通过时不得声称修复完成。无法完成部分检查时使用 `partial`、`failed` 或 `blocked`。

## change：功能与变更

适用于新功能、行为调整、迁移和维护性变更。

1. 明确目标、非目标、关键约束和成功标准。
2. 存量项目先核对代码、现有文档、工作区状态和已有失败，避免把旧问题算入新变更。
3. 按流程深度形成规格、方案和任务，获得授权后实施。
4. 优先交付可独立验证的最小价值切片，再处理后续切片。
5. 对照意图和实际 diff 评审，运行必要验证，更新受影响产物后交付。

实现中发现新信息时，可以回到规格、方案或任务修正，不必维护线性阶段的假象；但必须保留决策链并重新确认受影响的范围。

## review：只读评审与验收

适用于检查代码、规格、交付物或项目完成状态。

1. 明确评审对象、基准、原始意图和允许执行的操作。
2. 默认只读；修复、补测试、生成文件或改变任务状态需要另行授权。
3. 先列出有证据的发现，按严重度排序并给出文件或产物位置。
4. 区分需求缺失、实现错误、验证缺口、既有问题和风格偏好。
5. 给出 `verified`、`partial`、`failed` 或 `blocked`，不要将“未发现问题”写成“没有风险”。

## resume：恢复执行

适用于跨会话、上下文丢失、暂停后继续或状态可疑的项目。

1. 读取现有产物和适用的项目指令。
2. 核对真实文件、diff、版本控制状态、测试和运行结果。
3. 找出产物之间以及产物与工作区之间的冲突，不盲信完成勾选或旧摘要。
4. 经授权纠正状态，再从最近一个可信检查点继续。

状态文件是恢复索引，不是事实的替代来源。无法确认已执行操作时，按未确认处理，避免重复副作用。

## 流程深度

### 快速

适用于明确、低风险、可逆且单会话可完成的工作。

- 简短确认目标、范围和验收方式。
- 不强制创建规格目录。
- 仍须遵守修改授权并运行与风险相称的检查。

### 标准

适用于需要明确需求、技术方案或多个实施单元的连贯变更。

- 使用 `docs/specs/<change>/` 下的四类产物。
- 实施前完成规格与计划一致性检查。
- 每个价值切片独立验证，最终进行整体验证。

### 完整

适用于高风险、跨会话、跨系统、不可逆操作较多或需要协调的工作。

- 包含标准流程全部要求。
- 持续维护 `state.md`，记录可信恢复点。
- 根据风险使用 fresh-context 只读评审、隔离工作区和分阶段验收。
- 明确回滚、无人值守限制和停止条件；无可靠检查或权限边界时不得无人值守执行。
